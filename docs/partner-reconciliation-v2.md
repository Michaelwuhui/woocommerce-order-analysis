# 模块化合伙人对账 V2

## 历史对账草稿（2026-09-21 补充）

入口：模块化对账 → **历史对账草稿**。这是读取已出库 OMS 记录的草稿流程，与逐单启用货权后的正式权益账区分展示。规则和草稿保存到现有版本表 `rec_objects`，不需要新增 schema；只有内部、具备成本和对账编辑权限的人员可访问页面/API/导出。

先新增历史核算规则，明确实际仓库、供货方货权池、货值另账合同、本团队、费用服务商、期间、原订单管理费和各市场去程/回程物流费。按规则＋出库月份＋市场币种预览，确认后生成有独立编号的不可变草稿。CSV 从保存快照导出，后续订单或汇率变化不修改已有草稿。生成时复核预览摘要；请求重试使用相同编号，不重复创建。

本次确认口径：中转仓为黄总独资，团队承担全部商品及运费盈亏；黄总供货成本未提供，不能套用金毅金谷自备的波兰仓成本。出库即记销售收入，当前已确认拒收退回的订单收入归零。每原始订单收一次运费及管理费，拆包不加收；普通补发再收一次管理费，仓库漏发免收，原因不明列为待核实；补发不追加运费。补发分类需填写依据并保存入草稿，不从自由文本推断免收。各市场运费由规则输入，不修改现有全局退件设置。

人民币换算精确读取 `exchange_rates` 的当月值，缺失则取最近的更早月份，绝不借用未来汇率。每行展示实际汇率及来源月份，逐单舍入到分后汇总。源日期使用保存的出库日期字段；退回状态使用读取时的最新状态，因此草稿是历史回溯结果而非月末状态快照。

缺供货成本不按零处理：货值和商品利润为待定；已知服务商费用可先核对。来源数量不符、多仓、跨月分批、部分退回、退款歧义、汇率缺失、补发原因不明的行明确标记，不进入“已核实行合计”。回款必须另核资金凭证。历史草稿没有锁单、记账、核销接口，不会调整库存、修改旧对账或生成真实付款。不能与旧账重复结算。

历史规则只用于此历史草稿入口，不自动改变普通货权订单的费用配置。待成本齐全后的正式货值记账和旧账迁移仍需单独处理。

## 功能入口与日常流程

入口：**合伙人对账 → 模块化对账**，或 **系统设置 → 合伙人对账规则**。旧版对账单和收款记录继续使用原入口。新模块采用新增表，不搬迁历史账单，不根据仓库名称推断历史货权。

1. **合作规则**：登记本团队、合伙人、服务商、物流/代收方。同一主体可以承担多种角色。分别配置货权比例、回本比例、商品分润、亏损承担和运费收益归属。
2. **库存来源**：在已完成入库的实物批次上登记货权池和落地成本。未知成本留空；真实零成本填 `0`。未分批的已收库存可以分批登记，但不能凭空增加实物库存。
3. **合同和费用版本**：配置本团队备货、实际毛利、共同投资、固定供货价或旧销售比例模板。管理费按原订单/包裹计费，可选择出库、签收或账单核实时点、生效期间、站点、国家、仓库和渠道。20 CNY 只是演示规则，没有写成生产默认常量。
4. **启用订单**：选用货权池对应合同、费用版本、核算币种与汇率；多服务商明确选择主服务商、同一总额分摊或独立合同。无管理费需明确勾选确认，不能用漏配费率表示零。
5. **站点自动规则**：核对样板订单后可保存为站点规则，从指定订单日期起自动应用于新履约订单。最后保存版本生效；暂停只影响之后尚未启用的订单。已有履约、旧库存预留和已出库来源不会自动转换。单笔报价和指定批次不能复制成站点默认规则。
6. **预览和分仓**：预览事务会回滚；确认分仓才预留真实库存。支持本团队优先、少仓发货、先到期先发、完整报价成本、配额和人工指定批次。原有市场、SKU 专仓、启停及外部仓约束仍先执行。实际发货页面显示拣货批次与数量。
7. **物流账单与利润**：在原发货入口录入运单后，按包裹录入实际运费、逆向费、代收费、已代收、已回款及各自日期和凭证。商品来源、订单、站点、仓库、SKU、货权池可追溯；共同包裹账单只计算一次。
8. **确认权益**：检查待补全信息，再确认记账。成本、汇率、费用凭证缺失不能作为零结算。可补全成本、退款、真实其他费用和补发包裹；这类修订保留凭证和审计。
9. **对账与资金**：按主体、币种、结算时区和期间生成经营单或代收回款单，依次核对、确认、锁定、核销。负数账单、零金额活动、部分核销均支持。抵扣必须明确登记授权凭证，且只能在同主体同币种间操作。

## 金额和时间口径

- Woo `line_items.total` 为商品净额，`shipping_total` 和指定的运费/COD 附加费为客户运费收入；不把已经包含运费的订单总额再加一遍运费。税额用于守恒核对，不重复计入净收入。
- 波兰 25 PLN、捷克 200 CZK、匈牙利 2800/3200 HUF **没有写死**；读取每张订单的实际金额，包括免邮的零金额。
- 商品利润 = 净商品收入 − 已售来源成本/合同供货价 − 分摊管理费 − 已确认其他费用。商品退款只按核实后的累计净退款扣一次；可重新销售的退货回补原货权并冲回成本，损坏退货不恢复可售库存。
- 运费净收益 = 客户运费/COD 附加费净收入 − 实际物流费用 − 已确认运输相关费用。商品与运费收益分别分配，负利润按约定亏损比例处理。
- 管理费跨货权来源按选定权重分摊；分摊使用 Decimal 和稳定尾差分配。回本与利润比例独立，已付货款不再次形成回本应付。
- 金额存储为经校验的十进制文本，避开旧 PostgreSQL 兼容层把 NUMERIC 转为浮点的问题。商品权益使用订单选定核算币种，服务费、物流和代收账保留原币；汇率冻结进权益快照。
- 首次入账使用业务确认日期：商品依合同确认时点，按订单/主体/科目汇总时取相关来源最后确认时间；按订单管理费取首次满足时点的包裹，按包裹管理费汇总取最后相关包裹。物流代收、回款使用各自实际日期。后续修订追加本期差额，不修改已锁定记录。
- 默认显示贡献利润；只有明确确认经营费用完整归集，才显示“经营利润（已确认费用口径）”。不同币种和不同成本口径不直接合计。
- 实际净回款 `385 − 10 = 375` 会分别显示代收应回款 `−385`、已回款 `375`、物流应付 `10`；系统不擅自把两张单抵掉。
- 锁单前会再次检查期间相关订单是否待补全/待记账。期初余额用于展示，不重复计入本单应付。外部合作方的页面/API/CSV 仅显示本主体权益，不输出其他货权池成本快照。

## 库存边界

实物数量只有 `inv_stock`/`inv_batches` 一份；共有比例不会乘出更多库存。预留、出库、取消重分仓、退货都与 OMS 在同一事务内写来源和库存流水。PostgreSQL 对订单、库存和批次加锁，重试具有稳定业务键。

货权转让不移动仓库数量；“实物调拨收货”仅用于目标仓已经验收的调拨，减少原仓并增加目标仓，保留货权。在途运输证据仍由实际作业凭证管理。转让后的历史订单退货会恢复原货权，必要时创建对应的退回批次。

启用货权的仓库/SKU 不再允许旧库存处理器绕过来源扣减或预留。暂停站点新规则后，新订单也不会静默落到这些货权库存。无限量合作方来源应维持独立的原有仓库/来源配置。

## 安装和部署

代码按模块拆分：`reconciliation_core.py`（规则/金额）、`reconciliation_inventory.py`（来源库存）、`reconciliation_ledger.py`（经济与资金）、`reconciliation_api.py`（权限/API）、`reconciliation_schema.py`（新增表）。库存履约只增加少量接入点。

迁移必须显式执行，应用启动不自动改表：

```text
python scripts/migrate_reconciliation_v2.py --expected-database <实际数据库名>
```

执行环境使用项目既有受保护的 PostgreSQL 配置。先备份并走项目 PR 发布流程，再安装表；先核对一个站点、一个仓库/SKU 的实物批次和合同，再显式启用。回退时保留新增表和已发货来源，不能删掉货权流水或让旧处理器接管已有货权订单。暂停新站点规则只停止新增接入，不撤销已生效业务。

模块化基础功能已通过 PR #39 发布。历史对账草稿的补充流程见下文；历史草稿不修改真实库存，也不移动旧收款记录。

## 历史草稿的商品成本口径

历史草稿以 OMS 实际出库仓库、出库日期和订单商品为依据，从成本管理的 `product_costs` 匹配商品。只读取该仓库在出库日或之前生效的成本版本；品牌、口数必需吻合，有系列或口味限定的成本还需吻合相应字段。不跨仓库借成本，不使用出库之后才生效的成本，不把缺失成本当零。每个匹配结果在草稿快照中保留成本记录 ID、版本日期、原币和折算月份。

拒收退回订单的销售收入和本期应结供货货值为零，去程运费及管理费保留。正常已出库、尚未签收或回款的订单依合同计销售收入和商品成本，回款状态另行核对。普通补发只加管理费，不重复计商品货值或运费；仓库漏发补发免管理费。

每张草稿同时显示市场币种及人民币。商品成本与市场币种相同时先按该原币合计，再逐单折成人民币；不从已四舍五入的人民币倒推原币货值。`商品毛利`为商品净收入减供货货值；`团队贡献利润`再计入客户运费、物流费和管理费，仍未包括系统未收集的经营费用。成本不全时，仅显示已匹配商品的货值小计与缺失件数；整期供货货值、商品毛利及贡献利润保持待补全。系统内的价格是核对参考值，是否含头程、关税及供货方利润仍需业务凭证确认。草稿不可锁单、核销或重复记入正式权益账。旧草稿是生成当时的固定快照；新增或修订成本后需要重新预览并生成新草稿。
