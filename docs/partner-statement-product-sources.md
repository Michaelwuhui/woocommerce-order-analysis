# 合伙人账单：按商品供货来源核算

旧“实际毛利”账单曾按网站和币种把整单商品一起分成。金毅金谷中转业务需要区分：合伙人自己备货的商品继续返还成本并分润；我方备货、由对方代发的商品不返还对方备货成本、不分商品利润，只计约定打包费。同一款商品、同一订单也可能同时来自两个供货来源。

## 页面和生成流程

在原“合伙人对账”生成入口生成账单，金谷金毅（`poland_jin`）账单自动按商品行及 OMS 分仓数量拆分。账单列表标注“按商品来源 / 版本 / 待核实”，详情分别展示自备货分成、中转打包费和我方商品货款应收。

- 商品结算沿用旧账的下单月份和收入状态口径；打包费按实际出库月份独立核对，所以两者的订单数可能不同。
- 联合包裹按 `oms_shipment_items → oms_fulfillment_items` 判断是否包含中转商品，不能只看包裹主仓。
- 中转打包费读取出库日生效的 `partner_packing_rule` 版本：按本包裹实际发出的中转商品支数乘以每支单价。当前约定为每支 10 CNY；订单失败、取消、退款、退回以及补发均保留实际发生的打包费。原订单拆包分别按每包实际支数计费，联合包裹只计中转部分。
- 必须有实际出库时间、运单号和包裹商品数量凭证。仅创建面单不计费；同承运商及运单号的重复包裹合并核对，同一履约商品数量冲突则待核实。缺少支数不按零计费。商品来源确认不代表已经发货。
- 商品货款保留原市场币种；打包费单列 CNY，不自动从商品应收中抵扣。中转退件运费损失由我方另账显示，不作为合伙人的商品利润或自动报销。代收应交回和实际回款需要另核资金凭证。
- 未找到来源、分仓数量不符或自备货缺成本，明细显示待核实，不把未知成本当零。汇总明确标注“已核实行小计”，待补全并重新生成后才能确认、锁定或结清。
- 服务费流水逐包显示订单状态、商品、实发支数、单价及费用依据；原发或补发分类不影响逐支计费。旧版账单仍显示其生成时保存的费用和口径。

“按产品汇总 → 订单商品来源 → 中转打包费流水 → 修改前记录”使用同一冻结版本。商品来源、数量、履约单、成本记录及生效日、供货确认依据、包裹和费用规则均可追溯。Excel 使用同一快照，包含按产品来源、商品来源明细、中转打包费明细、打包商品明细、版本与口径等页签。

没有 OMS 记录的历史订单沿用原合伙人范围作为默认供货来源，并明确标注依据。业务方明确确认的个别商品可在现有不可变 `rec_objects` 中追加 `legacy_product_source` 记录：必须指明原订单、商品行、product_id、variation_id、数量、`partner_stock` 或 `transit_service`、确认依据。仅精确匹配的原商品行生效，不按商品名称推断所有同名订单，也不改变实物仓库、库存或发货记录；身份或数量改变时重新列为待核实。

逐支规则在 `rec_objects` 追加 `kind='partner_packing_rule'`：包含 `partner_id`、`warehouse_id`、`billing_basis='shipped_unit'`、`unit_fee_cny`、`effective_from`（含）、`effective_to`（不含）及约定依据，同期间最新版本生效。此规则仅作用于对应合伙人的中转打包费，不改其他合伙人、物流运费或 V2 历史草稿。没有逐支规则覆盖的历史日期继续使用原 `history_rule` 口径；已冻结版本不自动重算。

## 历史和并发保护

新表 `reconciliation_statement_versions` 只追加版本；既有账单、原订单快照在重新生成前完整保存到该版本的 `previous_json`。已确认、存在异议、锁定、结清或有收款的账单不能被重新生成覆盖。手工账单也不能覆盖已有冻结账单。旧账单未重新生成前显示原金额和“无商品来源快照”的说明，不后台悄悄更改金额。

PostgreSQL 生成使用同一可重复读事务和期间级事务锁，父账单、明细快照及审计原子提交。并发冲突返回 409，要求刷新后重试，不重复产生账单。分润尾差在整期内稳定分摊，逐行合计与整期约定比例一致，不把每行半分钱固定累积给同一方。

当前只有金谷金毅账单启用新分配规则。其他合伙人的生成口径保持原有计算，新增冻结经营明细供快速查看；已存在的模块化历史草稿不会自动记账或核销，不能与本账重复结算服务费。

## 性能和发布

打开已生成账单只读取小型汇总，不实时重算整月成本；产品、商品行和服务流水按冻结版本分页读取。旧订单快照与当前状态一次连接查询，避免每单一条查询。实时月报及订单成本识别一次读取系列并缓存商品解析结果，避免逐商品查询。月度订单列表始终分页，月度汇总另算，超过 5,000 单也不会截断。

发布前按项目流程备份、PR 审核及测试。显式应用 `migrations/postgresql/007_partner_statement_sources.sql`（使用既有维护角色），确认当前数据库名称后再执行。迁移只新增版本表和应用账号的 SELECT/INSERT 权限，不升级其他表、不导入业务行；应用启动不自动迁移 PostgreSQL。SQLite 测试初始化单独建表。

代码回退时保留版本表及确认记录，不删财务证据，不恢复旧库存数据。新增字段表明本账的来源口径；不要把新版商品结算小计解释为不含待核实项的全量经营销售。

验证：`tests/test_partner_statement_sources.py` 和 `tests/test_partner_statement_packing_units.py` 覆盖金额守恒、商品来源、联合包裹、逐支费用、各订单终态、拆包、跨月、补发、重复运单、凭证缺失、不可变版本、权限、导出和防覆盖；`tests/test_partner_statement_sources_postgres.py` 在显式启用的本地隔离库验证真实 OMS 表结构；`node --test tests/partner_statement_sources.test.cjs` 验证关键金额及页面输出。
